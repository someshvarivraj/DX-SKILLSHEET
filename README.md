# DX Skill Sheet

IIT採用者のスキルシートを作成・編集・出力するシステム。
Skill sheet generation system for engineers recruited from the Indian Institutes of Technology.

Built to `IITスキルシート生成システム_仕様書_0910.pdf`. The design principle behind every
decision here is the one the client asked for: **when the Google Form changes, the
application must not have to be rebuilt.** Which question feeds which position on the
sheet is configuration data, not code.

---

## Running it locally

Requirements: Node.js 20.11+ and Docker.

```bash
# 1. Database and a mail viewer
docker compose up -d

# 2. Configuration
cp .env.example .env

# 3. Install, create the schema, load the initial configuration
npm install
npm run db:migrate
npm run db:seed

# 4. Start
npm run dev
```

Open <http://localhost:3000>.

Sign in with the address in `SEED_ADMIN_EMAIL` (default `admin@example.com`). With
`MAIL_TRANSPORT=console` the login link is printed in the terminal running `npm run dev`
— copy it into the browser. Set `MAIL_TRANSPORT=smtp` with `SMTP_PORT=1025` to read the
mail in Mailpit at <http://localhost:8025> instead.

No AI account is needed. `AI_PROVIDER=mock` runs the whole pipeline with placeholder
Japanese so import, editing, review, versioning and PDF output can all be exercised.

## How the yearly form change is absorbed

This is the core requirement, so it is worth stating plainly.

1. **The form definition script is the input specification.** `scripts/parse-form-script.ts`
   executes `create_iit_form_YYYY.gs` against a stub of the Google `FormApp` API and
   records every question it creates — code, type, options, grid rows and columns. The
   2026 script yields all 113 questions. Next year: drop in the new `.gs`, run
   `npm run form:parse`, and the catalogue updates. No code change.

2. **The mapping lives in the database.** `SheetSection` and `SheetField` say what
   appears on the sheet, in what order, how it is processed, and which questions feed it
   (`SheetFieldSource`). All of it is edited at `/admin/fields`.

3. **Unassigned questions are surfaced, not dropped.** Both the import screen and the
   field definition screen list questions that no field consumes, so a change to the form
   cannot be missed.

4. **Generation prompts are data too.** Operators tune the AI output from the screen.

## What the system does

```
Googleフォーム回答 (CSV/XLSX)
        │  ← manual, explicit import; never an automatic sync
        ▼
  取り込み層 FormResponse        raw answers, written once, read-only afterwards
        │
        ▼  processing: 転記 / 辞書 / 補完 / 翻訳 / 生成 / 規則生成 / 手入力
  編集層 FieldValue              the authoritative content, per-field history + lock
        │
        ▼  下書き → 確定
  SheetVersion                   every save is a version; only 確定 can be exported
        │
        ▼
  PDF (headless Chromium, same HTML as the preview)
```

### Processing types

| Type | Behaviour | AI |
|---|---|---|
| 転記 COPY | Copy the answer; strip the `A1. ` marker and the English half of bilingual options | no |
| 辞書 GLOSSARY | Substitute from the glossary table | no |
| 補完 ENRICH | Copy, then add what the system knows (hometown → state → region) | no |
| 翻訳 TRANSLATE | Translate faithfully, never summarise (publications, patents) | yes |
| 生成 GENERATE | Translate, simplify, write for non-specialists | yes |
| 規則生成 RULE_BASED | Deterministic (JLPT description, age) | no |
| 手入力 MANUAL | Typed in by staff | no |

### Things that are deliberately not AI

- **The JLPT ability paragraph** is generated by rule from the score breakdown, using the
  official pass marks and section minimums for N1–N5. The same input always produces the
  same sentence, so review is possible. `src/lib/rules/jlpt.ts`, tested in `tests/jlpt.test.ts`.
- **Hometown → region** comes from the supplied table. The glossary file notes that
  letting an AI decide produced the same state in two different regions.
- **Terminology** comes from the glossary, both before and after the AI call.
- **Orthography** (full-width punctuation, half-width numerals, no space between Japanese
  and Latin) is applied mechanically. `src/lib/style/text.ts`.

## Roles

| Role | Can do |
|---|---|
| 管理者 ADMIN | Everything: definitions, import, edit, finalise, export, users |
| 営業 SALES | Edit sheets, choose which records are shown per recipient, export |
| 技術者（本人） ENGINEER | Edit their own internship and project records, submit for review |
| 閲覧のみ VIEWER | Read-only — the shared demo account |

Sign-in is a one-time link sent to a company email address; no password is stored. The
demo account is the single exception and is read-only.
